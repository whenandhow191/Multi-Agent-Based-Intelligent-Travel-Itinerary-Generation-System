## 2. 隔离开发环境

### 2.1 为什么使用两层隔离

根据项目方案，CI 与依赖锁定使用 uv；根据本机开发需求，再用项目内 Conda 环境隔离 Python 3.12 和 uv。这样不会修改 base Conda 或系统 Python：

```text
.conda/env   -> 项目专用 Python 3.12 + uv 引导工具
.venv        -> uv 根据 uv.lock 创建的项目依赖环境
node_modules -> pnpm 根据 pnpm-lock.yaml 创建的前端依赖
```

三者都在 `.gitignore` 中，不会上传 GitHub。

### 2.2 新机器复现

在仓库根目录执行：

```powershell
conda env create --prefix .\.conda\env --file environment.yml
conda activate .\.conda\env
uv sync --all-groups --frozen
pnpm install --frozen-lockfile
Copy-Item .env.example .env
pnpm check
```

如果环境已经存在，跳过第一条。更新 `pyproject.toml` 后运行 `uv lock`；更新任一 `package.json` 后运行 `pnpm install`，并一起提交相应锁文件。

## 5. C02：开发工具链与 CI

提交信息：`build: configure development toolchain and ci`

### 做了什么

- `environment.yml` 固定 Conda Python 3.12 引导环境。
- `pyproject.toml` 声明 Python 版本、开发依赖和 Ruff/mypy/pytest 规则。
- `uv.lock` 锁定 Python 间接依赖。
- `package.json` 和 pnpm workspace 提供统一任务入口。
- `.editorconfig`、`.gitattributes` 统一 UTF-8、LF、缩进和文件属性。
- `.pre-commit-config.yaml` 在本地提交前重放质量检查。
- GitHub Actions 使用 Python 3.12、Node 22、uv 和 pnpm 11，执行与本地相同的 `pnpm check`。

### 每个命令做什么

| 命令 | 作用 |
|---|---|
| `pnpm format` | Ruff 格式化 Python，Prettier 格式化 Web 源码 |
| `pnpm lint` | Ruff 检查 Python，ESLint 检查 TypeScript/React |
| `pnpm typecheck` | mypy 严格检查 Python，tsc 检查前端 |
| `pnpm test` | pytest 与 Vitest 测试 |
| `pnpm build` | 生成 Web 生产构建 |
| `pnpm check` | 以 CI 顺序执行以上只读检查和构建 |

安装 Git hook（可选但推荐）：

```powershell
uv run pre-commit install
```

## 6. C03：本地开发运行时

提交信息：`build: add local development runtime`

### FastAPI

`apps/api/main.py` 创建应用并提供 `GET /health`。返回固定、可测试的 JSON：

```json
{"status":"ok","service":"travel-api","version":"0.1.0"}
```

health 不依赖数据库或外部 API，所以可区分“进程是否存活”与“某个依赖是否故障”。

### React

`apps/web` 使用 React + TypeScript + Vite。占位页展示项目定位，并调用 API health 显示在线/离线状态。Vitest 用 Mock fetch 验证成功路径，Vite build 验证生产产物可生成。

### Docker Compose

三个服务及启动顺序：

```text
PostgreSQL healthy -> FastAPI healthy -> Web/Nginx healthy
```

启动：

```powershell
docker compose up --build -d
docker compose ps
Invoke-RestMethod http://localhost:8000/health
Start-Process http://localhost:5173
```

停止但保留数据库 volume：

```powershell
docker compose down
```

### 本次机器上的容器复验说明

`docker compose config --quiet` 已通过，API/Web 单元测试与 Web 生产构建已通过。首次拉取镜像时，Docker Desktop 当前配置的代理 `127.0.0.1:7897` 没有监听，导致 Docker Hub 连接失败。恢复该代理，或由你在 Docker Desktop 设置中关闭这个失效代理后，再执行 `docker compose up --build -d` 即可完成镜像级复验。项目没有自动修改全局 Docker 代理。

## 7. C04：类型化配置与密钥检查

提交信息：`feat: add typed configuration and secret checks`

### 配置优先级

从低到高依次为：

```text
代码安全默认值
  -> .env
  -> .env.{APP_ENV}
  -> .env.local
  -> 进程环境变量
```

`APP_ENV` 只允许 `development`、`test`、`production`。生产环境若打开 `DEBUG` 会在启动时失败。API 在模块装配时调用 `get_settings()`，因此类型错误不会被拖到首次请求才暴露。

### 密钥安全

- 服务端 Key 和数据库 URL 使用 `SecretStr`，`repr` 不显示原文。
- `.env.example` 只有变量名和本地非生产默认值。
- `.env`、`.env.production`、`.env.local` 等都被 Git 忽略。
- 前端高德 JS Key 与服务端 Web Service Key 分开，未来必须使用最小权限和域名白名单。

运行 doctor：

```powershell
python -m apps.api.config doctor
```

无外部 Key 的默认输出仍是 ready，因为第一章采用 Mock 模式。输出只包含 `present/missing` 与 `required/optional`，不会打印值。

### 何时写 ADR

当选择影响多个模块、引入长期约束或难以回滚时写 ADR，例如数据库队列、消息语义、模型网关协议、坐标标准和供应商存储策略。普通重命名、局部修复不需要 ADR。
