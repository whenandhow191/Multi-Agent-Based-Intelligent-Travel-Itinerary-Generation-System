# ADR-0001：工程基础与本地运行时

- 状态：Accepted
- 日期：2026-09-12
- 决策者：项目维护者
- 关联检查点：C00～C05

## 背景

项目从只有设计文档的仓库开始，需要建立后续 49 个检查点都能复用的目录、依赖、质量门禁、最小服务和密钥边界。开发机器已有 Conda、Node、pnpm 和 Docker，但不应污染全局 Python 环境。

## 决策驱动因素

- 本地与 CI 使用同一条验证命令。
- 没有外部 API Key 时也能启动并测试。
- Python 与 Node 依赖可复现，不写入全局环境。
- 目录提前表达应用、领域、Harness、Agent、工具和评测的边界。
- 配置错误在启动时暴露，密钥不进入日志和诊断输出。

## 考虑过的方案

### 单目录 Python 应用

初期文件较少，但会让 API、Agent、工具和领域模型快速耦合，后续拆分代价高。

### 一开始建立多个独立发布包

边界最强，但第一章需要维护多个构建元数据，增加与当前学习目标无关的复杂度。

### 可导入的 monorepo 边界（采用）

在 `apps/` 和 `packages/` 下建立 Python 包边界，当前由根 `pyproject.toml` 管理，等模块形成独立发布需求后再拆包。

## 决策

1. 使用 `apps/api`、`apps/web` 与 `packages/{domain,harness,agents,tools,evals}` 的 monorepo。
2. 本机使用仓库内 `.conda/env` 提供 Python 3.12 和 uv；uv 再依据 `uv.lock` 管理项目虚拟环境，二者都被 Git 忽略。
3. Node 使用 pnpm workspace 和锁文件；唯一质量入口为 `pnpm check`。
4. 本地运行时由 Docker Compose 提供 PostgreSQL 16、FastAPI 和 Nginx 承载的 React 页面。
5. 配置使用 Pydantic Settings；服务端密钥用 `SecretStr`，doctor 只报告是否存在。
6. 采用 MIT License，使用结构化 Issue/PR 模板和 Conventional Commits。

## 后果

### 正面

- 后续代码有明确落点，依赖方向可以自动检查并逐步加强。
- 本地、CI 和容器都由锁文件得到一致依赖。
- 开发不修改 base Conda 或系统 Python。
- Mock 模式允许无 Key 演示，真实供应商接入可延后。

### 负面与风险

- Conda 引导环境与 uv 项目环境是两层隔离，需要在文档中解释。
- Docker 首次启动需要下载镜像，受本机代理和网络状态影响。
- 当前根 Python 包布局适合教学初期；若未来要独立发布，需要新增打包 ADR。

## 验证方式

```powershell
conda run --prefix .\.conda\env python --version
pnpm check
python -m apps.api.config doctor
docker compose config --quiet
```

完整容器验证使用 `docker compose up --build`，随后访问 API `http://localhost:8000/health` 和 Web `http://localhost:5173`。

## 复审条件

- 共享包需要独立发布或由多个仓库消费。
- CI 时间因双生态安装不可接受。
- 单机 Compose 不再满足团队或部署环境需求。
- Python、Node 或 PostgreSQL 的受支持版本发生破坏性变化。
