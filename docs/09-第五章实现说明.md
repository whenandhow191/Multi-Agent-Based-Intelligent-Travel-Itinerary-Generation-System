# 第五章“共享黑板与 1+4 协作”实现说明

> 对应开发路线：C23～C26
> 完成日期：2026-09-13
> 里程碑：`v0.2.0`
> 目标：说明 Artifact Blackboard、1+4 fan-out/fan-in、局部返工和确定性最终聚合的实现与复现方法

## 1. 完成结果

第五章把第四章五个独立组件连接成可追溯、可局部返工、无需最终润色模型也能输出完整方案的工作流：

```text
                     +--> A1 Destination --+
TripRequest -> Coord |                     +--> Route Matrix -> A3 -> A4
                     +--> A2 Mobility -----+                       |
                                                                   +-- pass -> FinalAggregator
                                                                   +-- revise -> RepairController
                                                                                   |
                                                          Blackboard v2 <- affected tasks only
```

关键结果：

- 所有大结果写入 Blackboard，任务间只传小型 `ArtifactRef`。
- A1/A2 真并行，Route Matrix 必须等待两者完成；A3/A4 严格 fan-in。
- 每个 Artifact 都有不可变版本、canonical JSON 哈希和父 Artifact lineage。
- PatchRequest 只使责任 Agent 及其下游失效，最多修订两轮。
- 用户澄清会进入 `WAITING_USER`，收到字段级答案后从受影响分支恢复。
- FinalAggregator 只接受 A4 PASS 且最终确定性复验通过的方案。
- JSON 和 Markdown 从同一个 `FinalPlanBundle` 渲染，不需要模型润色。

## 2. C23：共享 Artifact Blackboard

提交：`feat(harness): implement shared artifact blackboard`

主要文件：

| 文件 | 作用 |
|---|---|
| `packages/harness/blackboard.py` | Blackboard 协议、ArtifactRecord、内容哈希、内存/PostgreSQL 实现和 lineage |
| `packages/harness/blackboard_cli.py` | C23 最小 PostgreSQL 读写 CLI |
| `packages/harness/persistence/schema.py` | SQLAlchemy `artifact_heads`、`artifacts`、`artifact_parents` 表 |
| `migrations/versions/0003_artifact_blackboard.py` | 对应 Alembic migration |
| `tests/test_blackboard.py` | 内存版本、哈希、lineage、并发冲突与 CLI 参数测试 |
| `tests/test_postgres_blackboard.py` | PostgreSQL 真实并发写入测试 |

### 2.1 ArtifactRecord

每个记录包含：

- `artifact_id`：全局地址。
- `run_id/task_id/artifact_type/version`：逻辑读取键。
- `producer_agent` 与 `schema_version`：生产者和契约版本。
- `parent_artifact_ids`：直接输入的 lineage。
- `content_hash`：对 payload 使用 UTF-8、排序键和紧凑分隔符后计算的 SHA-256。
- `payload/created_at`：允许持久化的结构化内容和创建时间。

构造时会重算哈希；payload 被修改但 hash 未变时，Pydantic 直接拒绝。父 ID 不可重复、不可引用自己，也不能跨 run。

### 2.2 并发版本保护

内存实现使用 `asyncio.Lock`。PostgreSQL 实现不是只依靠最终唯一约束，而是在一个事务内：

1. 确保 `(run_id, task_id, artifact_type)` 的 `artifact_heads` 行存在。
2. `SELECT ... FOR UPDATE` 锁住版本头。
3. 同时检查调用方 `expected_latest_version` 和待写 `version == current + 1`。
4. 写 Artifact 与父边。
5. 更新版本头并提交。

因此两个 Worker 同时以 `expected_latest_version=0` 写 version 1 时，只会有一个成功，另一个得到 `ArtifactVersionConflictError`。

### 2.3 CLI

完成 migration 后可用完整逻辑键操作：

```powershell
python -m packages.harness.blackboard_cli `
  --database-url $env:TEST_DATABASE_URL `
  put --file .\artifact.json --expected-latest-version 0

python -m packages.harness.blackboard_cli `
  --database-url $env:TEST_DATABASE_URL `
  get --run-id run_demo --task-id task_demo --type destination_intel --version 1
```

CLI 只做诊断适配，不用 `shell=True` 拼接命令。完整 `travelctl` 仍按 C32 实现。

## 3. C24：1+4 fan-out/fan-in

提交：`feat(workflow): orchestrate one plus four agents`

主文件：`packages/workflow/orchestrator.py`。

`OnePlusFourWorkflow` 注入五个供应商无关 callable，并按固定顺序运行：

1. 使用 `asyncio.gather()` 同时启动 A1 `destination` 与 A2 `mobility`。
2. 两者各自完成 Schema 校验并把 version 1 写入 Blackboard。
3. fan-in 后由 Harness 调用 `build_route_matrix`；`RouteMatrixArtifact` 只接受合并候选中的端点。
4. A3 读取 A1、A2 与 Route Matrix 的结构化对象生成候选。
5. A4 读取候选和事实进行审校。
6. 每一步发布 ArtifactRef，并把直接输入记录为父 Artifact。

`WorkflowTrace` 只保存 task、开始/结束时间和输入/输出 ArtifactRef，不保存模型私有思维链。`tests/test_one_plus_four_workflow.py` 使用同步屏障：A1/A2 必须都启动后才允许任一返回，因此能证明真实并行；测试还从 Review 反向追溯整条 lineage。

## 4. C25：局部返工和澄清恢复

提交：`feat(workflow): add targeted repair and invalidation`

主文件：`packages/workflow/repair.py`。

### 4.1 失效传播

固定依赖图为：

```text
A1 --------+
           +--> Route Matrix --> A3 --> A4
A2 --------+
```

`TargetedRepairController` 先把 PatchRequest 的 `target_agent` 映射到任务，再计算依赖闭包：

| 问题归属 | 重跑 | 复用 |
|---|---|---|
| A1 事实 | A1、Route Matrix、A3、A4 | A2 |
| A2 酒店/交通 | A2、Route Matrix、A3、A4 | A1 |
| A3 排程/预算 | A3、A4 | A1、A2、Route Matrix |
| A4 自身审校 | A4 | A1、A2、Route Matrix、A3 |
| Coordinator/用户矛盾 | 先 `WAITING_USER` | 暂不重跑 |

执行时按依赖顺序调用 handler。handler 只能看到当前 PatchRequest 和上游 ArtifactRef；新 Artifact 必须等于 Blackboard 当前版本加一，否则拒绝。

### 4.2 两轮上限

`completed_revision_rounds >= 2` 时抛出 `RevisionLimitExceededError`，不会开启第三轮或无限循环。版本冲突同样不会自动覆盖其他 Worker 结果。

### 4.3 人工澄清

Coordinator 类型 Patch 会生成 `RepairStatus.WAITING_USER`，记录待确认字段而不失效 Artifact。`resume_after_clarification()` 要求非空字段答案：只修改 lodging/transport 时从 A2 分支恢复，只修改 destination 时从 A1 分支恢复，范围不明确时安全地重跑 A1/A2 及其下游。

`tests/test_targeted_repair.py` 验证酒店修改不会重跑 A1、新 Route Matrix 同时引用 A1 v1 与 A2 v2、人工澄清恢复，以及第三轮被拒绝。

## 5. C26：FinalAggregator

提交：`feat(workflow): add verified final aggregation`

主文件：`packages/workflow/final_aggregator.py`。

聚合顺序：

1. 检查 A1/A2/A3/A4 的 `run_id` 一致。
2. 只接受 `ReviewVerdict.PASS`，并要求 Review 覆盖所有候选计划。
3. 要求每个计划完整覆盖旅行日期。
4. 合并 A1/A2 Evidence；同 ID 不同内容属于冲突并阻断。
5. 对每个计划重新运行 `validate_itinerary()`，检查预算、时间窗、重叠、闭馆、坐标系及 Place/Route/Claim/Evidence 引用。
6. 使用 A4 的最终评分，计算活动数、通勤时间、空闲时间、费用、偏好覆盖、风险数和证据覆盖率。
7. 汇总 Evidence 新鲜度、显式 unknown/执行前确认项和协作摘要。
8. 创建唯一的 `FinalPlanBundle`，再从它渲染 canonical JSON 和确定性 Markdown。

最终聚合没有模型依赖。即使有人伪造 PASS Review，只要计划缺 Evidence 或违反硬约束，FinalAggregator 仍会以 `deterministic_validation_failed` 阻断。

`tests/test_final_aggregator.py` 验证三方案比较、JSON 往返、Markdown 字节级稳定、关闭润色模型仍完整，以及非 PASS/缺 Evidence 必须失败。

## 6. 文件调用关系

```text
packages/workflow/orchestrator.py
  ├─ packages/agents/*
  ├─ packages/harness/blackboard.py
  └─ packages/workflow/repair.py
       └─ Blackboard latest/write

packages/workflow/final_aggregator.py
  ├─ packages/domain/validators.py
  ├─ PlanCandidatesArtifact + ReviewArtifact
  └─ FinalPlanBundle -> JSON + Markdown
```

Workflow 不直接依赖 Provider SDK。真实 Model/Tool Adapter 接入后，只需要替换 `WorkflowServices` 中的 callable，不改变 Blackboard、返工和最终校验。
