# 第八章实现说明：后端与前端产品化

> 对应检查点：C39～C44  
> 完成日期：2026-09-21  
> 里程碑：`v0.4.0`

## 1. 本章交付结果

第八章把前七章的领域契约、1+4 Harness、共享 Blackboard、真实工具边界和模型治理能力包装成可操作的产品界面。当前默认使用纯合成 Fixture，因此无需模型 Key 也能从需求表单走完创建运行、查看协作、比较方案、局部修改、恢复版本和导出结果的全过程。

```text
React 产品界面
  -> 类型化 API Client（幂等键 + 匿名运行令牌）
  -> FastAPI Trip Run API
  -> Run Service
  -> Domain / Harness / FinalAggregator / Fixture
```

前端只渲染后端返回的结构化事实，不自行计算路线、预算、开放时间或方案可行性。

## 2. C39：Trip Run API

提交：`feat(api): expose trip run endpoints`

主要文件：

- `apps/api/run_models.py`：Trip Run 创建、状态、澄清、结果和比较 Schema。
- `apps/api/run_service.py`：内存 Fixture 组合根，生成三个可比较方案。
- `apps/api/run_routes.py`：FastAPI 路由与 OpenAPI 描述。
- `apps/api/main.py`：挂载 `/api/v1/runs` 路由并升级 API 版本。
- `tests/test_trip_run_api.py`：完整 OpenAPI Fixture 流程测试。

提供的基础端点：

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/runs` | 创建一次运行 |
| GET | `/api/v1/runs/{run_id}` | 读取状态 |
| POST | `/api/v1/runs/{run_id}/cancel` | 取消运行 |
| POST | `/api/v1/runs/{run_id}/clarifications` | 回答结构化澄清问题 |
| GET | `/api/v1/runs/{run_id}/result` | 获取同源 JSON/Markdown 结果 |
| GET | `/api/v1/runs/{run_id}/comparison` | 获取方案比较指标 |

Fixture 模式明确限制为北京一日合成案例，防止演示数据被误认为任意目的地的实时事实。

## 3. C40：SSE、安全与生命周期

提交：`feat(api): add progress security and lifecycle`

每次创建运行会返回一次匿名 `access_token`。后续请求通过 `X-Run-Token` 发送；服务端仅保存 SHA-256 摘要，并使用常量时间比较。错误令牌返回与不存在运行一致的 404，避免枚举其他人的运行。

创建请求必须包含 `Idempotency-Key`。同一 Key 和相同请求返回原运行，不重复生成；同一 Key 搭配不同请求返回 409。

新增端点：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/v1/runs/{run_id}/events` | SSE 进度流 |
| DELETE | `/api/v1/runs/{run_id}` | 删除运行 |

SSE 只包含任务 ID、Agent ID、状态、公开消息、工具名、Artifact ID 和成本估算，不包含 Prompt、chain-of-thought、密钥或供应商原始响应。

## 4. C41：需求与运行状态页面

提交：`feat(web): add trip request and run status pages`

主要文件：

- `apps/web/src/api.ts`：统一处理 API 地址、错误、幂等键和匿名令牌。
- `apps/web/src/types.ts`：与公开 API 对齐的 TypeScript 类型。
- `apps/web/src/components/TripRequestForm.tsx`：受控表单，构造完整 `TripRequest`。
- `apps/web/src/components/RunStatus.tsx`：展示状态、运行编号、模式和结果可用性。
- `apps/web/src/App.tsx`：页面组合、健康检查、会话状态和错误降级。

匿名令牌只写入 `sessionStorage`，不会进入 URL、React 展示文本或日志。API 离线、请求失败和服务端业务冲突都有明确页面反馈。

## 5. C42：1+4 协作调试页

提交：`feat(web): visualize agent collaboration`

`CollaborationPanel.tsx` 从 SSE trace 呈现：

- A0 Coordinator 与 A1～A4 的完成状态；
- A1/A2 fan-out、路线矩阵、A3、A4 的 Task DAG；
- 归一化工具调用摘要；
- Artifact 发布顺序和 lineage；
- 每阶段及总成本估算。

这页展示的是可公开的结构化 trace，而不是模型私有推理。它能直接证明五个 Agent 是否按预期协作。

## 6. C43：攻略、地图与方案比较

提交：`feat(web): render itinerary map and comparison`

`ItineraryExplorer.tsx` 使用同一份 `FinalPlanBundle` 渲染三个候选方案、逐日活动、预算、通勤、空闲、风险、证据覆盖和证据来源。后端额外返回只读 `MapPoint`；时间轴与地图均以 `place_id` 关联，因此点选日程会高亮唯一对应点位。

当前地图是无需第三方 SDK 的 GCJ-02 合成坐标示意，既可离线测试，也不会把服务端高德 Web Service Key 放进浏览器。后续替换为高德 JS SDK 时仍复用相同 `place_id` 和坐标契约。

## 7. C44：局部重规划、版本与导出

提交：`feat(web): add replanning versions and exports`

新增端点：

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/runs/{run_id}/replan` | 提交自然语言修改 |
| GET | `/api/v1/runs/{run_id}/versions` | 列出版本及受影响任务 |
| GET | `/api/v1/runs/{run_id}/versions/diff?from=1&to=2` | 结构化路径差异 |
| POST | `/api/v1/runs/{run_id}/versions/{version}/restore` | 恢复已有版本 |
| GET | `/api/v1/runs/{run_id}/export?format=markdown|json` | 下载导出 |

“第二天轻松一点”在 Fixture 中只失效并重新生成：

```text
itinerary_planning -> critic_review -> final_aggregation
```

`destination_intelligence`、`mobility_lodging` 和路线事实不会重跑。每次修改保存 instruction、受影响任务、失效 Artifact 和结构化 JSON 路径差异；最多允许两轮修改，与 C25 的返工上限一致。

`ReplanningPanel.tsx` 提供自然语言输入、版本历史、当前版本标记、差异预览、恢复按钮以及 Markdown/JSON 下载。

## 8. 安全与数据边界

- React 永远不接触 `DEEPSEEK_API_KEY`、`OPENAI_API_KEY` 或高德 Web Service Key。
- 匿名令牌不放在查询字符串；SSE 使用 Fetch Header，而不是会把令牌放进 URL 的原生 EventSource。
- Fixture 页面持续显示“合成数据，不代表实时价格或库存”。
- 导出的 Markdown 和 JSON 来自同一个已校验 `FinalPlanBundle`。
- 地图点位、日程、比较和证据通过稳定 ID 关联，前端不重新推断事实。
