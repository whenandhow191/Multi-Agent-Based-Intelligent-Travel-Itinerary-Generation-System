# 部署与发布说明

## 1. 支持的运行方式

### 方式 A：Docker Compose（推荐演示）

要求 Docker Desktop 或 Docker Engine + Compose plugin。

```powershell
Copy-Item .env.example .env
docker compose config --quiet
docker compose up --build -d
docker compose ps
```

访问：Web `http://localhost:5173`，API `http://localhost:8000`，Swagger `http://localhost:8000/docs`。

默认 `MOCK_MODE=true`，会使用合成 Fixture。普通停机：

```powershell
docker compose down
```

只有确认不再需要本机 PostgreSQL 数据时才执行：

```powershell
docker compose down --volumes
```

### 方式 B：项目独立 Conda 环境

```powershell
conda env create --prefix .\.conda\env --file environment.yml
conda activate .\.conda\env
uv sync --active --all-groups --frozen
pnpm install --frozen-lockfile
Copy-Item .env.example .env
python -m apps.api.config doctor
pnpm demo
```

分别启动后端和前端：

```powershell
python -m uvicorn apps.api.main:app --host 0.0.0.0 --port 8000
pnpm --filter @travel/web dev
```

## 2. 真实 Provider 配置

所有值只放在本机 `.env` 或部署平台 Secret；不要通过聊天、Issue、Commit、CI 日志传递原值。

| 变量 | 用途 | 是否必需 |
|---|---|---|
| `DATABASE_URL` | PostgreSQL 连接 | 是 |
| `DEEPSEEK_API_KEY` | 默认模型 Provider | 真实模型模式必需 |
| `OPENAI_API_KEY` | 高级/回退模型 | 可选 |
| `AMAP_WEB_SERVICE_KEY` | 服务端 POI/地理编码/路线 | 真实高德模式必需 |
| `QWEATHER_API_KEY` | 可选天气 Provider | 可选；Open-Meteo 无 Key |
| `AMAP_JS_KEY` | 浏览器地图 SDK | 可选且必须使用独立 Key |

建议上线前：

1. 轮换任何曾在截图或聊天中展示的 Key。
2. 高德服务端 Key 仅开通必需服务并设置配额/IP 策略；浏览器 Key 单独创建并限制域名。
3. 设置强 `POSTGRES_PASSWORD`，不要使用 Compose 本地默认值。
4. 设置 `APP_ENV=production`、`DEBUG=false`、明确的 `WEB_ORIGINS`。
5. 使用 `python -m apps.api.config doctor` 只检查 present/missing；该命令不会显示值。

## 3. 迁移、健康与回滚

发布前执行：

```powershell
pnpm check
pnpm demo
docker compose config --quiet
```

Compose 的 `migrate` 服务会在 API 启动前执行 `alembic upgrade head`。健康端点为 `/health`，响应必须包含 `version: 1.0.0`。

回滚流程：

1. 保留 PostgreSQL 卷并备份数据库。
2. 检出上一个已验证 Tag。
3. 使用该 Tag 的镜像/代码重新启动。
4. 数据库降级不是自动动作；先检查 Alembic migration 的向后兼容性，再决定是否 downgrade。

## 4. GitHub Release

```powershell
git tag -a v1.0.0 -m "release: v1.0.0"
git push origin master
git push origin v1.0.0
```

Tag 会触发 `.github/workflows/release.yml`。工作流只有在安装锁定依赖、数据库迁移、`pnpm check`、`pnpm demo`、Compose 校验和两个 Docker 镜像构建全部成功后，才创建 GitHub Release。

## 5. 故障定位顺序

1. `docker compose ps` 检查 db/migrate/api/web。
2. `docker compose logs migrate api web` 查看结构化错误；不要粘贴包含密钥的完整日志。
3. `python -m apps.api.config doctor` 检查变量是否存在。
4. `/health` 成功但页面失败时，检查 `VITE_API_BASE_URL` 与 `WEB_ORIGINS`。
5. Provider 失败时查看结构化 routing attempts、partial 状态和 OTel span，不查看或保存原始 Prompt。
