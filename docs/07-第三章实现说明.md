# 第三章“自建 Harness 内核”实现说明

> 对应开发路线：C12～C17  
> 完成日期：2026-09-12  
> 里程碑：`v0.1.0`  
> 目标：说明统一 Gateway、Agent 循环、DAG 调度、PostgreSQL 持久化和崩溃恢复如何完成

## 1. 完成结果

第三章把第二章的静态契约连接成了可执行、可持久、可恢复的 Harness 内核：

- Agent 只认识统一 `ModelGateway`，不直接依赖任何真实模型厂商。
- 模型只能请求工具；`ToolGateway` 决定工具是否存在、当前 Agent 是否有权调用，以及参数/结果是否满足 Schema。
- `BaseAgent` 限制总步骤、工具调用数和墙钟时间，只接受结构化最终输出。
- `TaskDAG` 在运行前检查缺失依赖与环；Scheduler 并发执行独立任务并按依赖顺序推进。
- PostgreSQL migration 建立运行、任务、依赖、事件、检查点和 Outbox 表。
- 多 Worker 通过行锁与原子更新领取任务，不会同时获得同一租约。
- heartbeat、检查点和过期租约恢复允许新 Worker 从最近一步继续。
- 事件与 Outbox 在同一事务提交，publisher 使用租约避免并发重复发布。

本次本地 `pnpm check` 实际结果为 Python 61 个测试通过、1 个 PostgreSQL 集成测试按设计跳过，Web 1 个测试通过；Ruff、ESLint、mypy、TypeScript 和 Vite 生产构建全部通过。被跳过的用例会在 GitHub Actions 的 PostgreSQL 16 service 上强制执行。

总体调用关系：

```text
TaskDAG -> DagScheduler -> BaseAgent
                         ├─ ModelGateway -> Provider Adapter（后续）
                         └─ ToolGateway  -> registered Tool Handler

Worker -> HarnessRepository -> PostgreSQL
          ├─ task lease / heartbeat
          ├─ checkpoint
          ├─ append-only event
          └─ transactional outbox -> publisher -> event consumer
```

## 3. C12：ModelGateway

提交信息：`feat(harness): add model gateway contract`

`packages/harness/model_gateway.py` 定义统一模型边界：

- `ModelMessage` 与角色枚举。
- `ModelToolSpec` 与 `ModelToolCall`。
- `ModelPolicy`：模型别名、温度、输出 token、超时和工具调用预算。
- `TraceContext`：run/task/trace 关联 ID。
- `ModelUsage`：输入、输出、缓存、推理 token 和成本微单位，可跨步骤相加。
- `ModelRequest` 与 `ModelTurn`：拒绝“同时返回工具调用和最终输出”等歧义形状。
- `ModelGateway`：只有一个异步 `generate()` 协议。

`ScriptedModelGateway` 是离线实现，按顺序返回预校验 `ModelTurn` 并记录请求。后续接入 OpenAI、Ollama 或 vLLM 时，业务 Agent 无需改变。

## 4. C13：ToolGateway

提交信息：`feat(harness): add tool gateway and registry`

工具执行顺序固定为：

```text
Agent allowlist -> registry lookup -> input Schema -> handler -> output Schema
```

任一步失败都会抛出稳定分类，不会尝试猜测或修补非法参数。`ToolRegistry` 拒绝同名覆盖，并只向模型暴露名称、描述和输入 JSON Schema；Handler、本地配置与密钥不会进入提示上下文。

内置 `fixture.echo` 不访问网络、环境或文件，用于证明工具发现、允许执行、越权拒绝、额外字段拒绝和输出校验。

## 5. C14：Agent 生命周期

提交信息：`feat(harness): implement base agent lifecycle`

`BaseAgent` 每一步执行：

1. 组合 system message 与不可变 `AgentContext`。
2. 只附加当前 Agent allowlist 中的工具 Schema。
3. 通过 `ModelGateway` 获取一轮结构化响应并累计 Usage。
4. 若有工具请求，经 `ToolGateway` 执行并把 JSON 结果加入新上下文。
5. 若有最终输出，用 Agent 声明的 Pydantic 类型重新校验后返回。

循环受 `max_steps`、`max_tool_calls` 和 `timeout_seconds` 三重限制。失败分为模型、工具策略、工具执行、输出 Schema、步骤上限、调用上限和超时；每类同时声明是否可重试。

`EchoAgent` 测试了直接完成、工具后完成、非法结构化输出、无限工具循环被截断和超时。

## 6. C15：DAG Scheduler

提交信息：`feat(harness): add dag scheduler and retries`

`TaskDAG` 构造时拒绝：

- 空图、重复 ID 或超过节点上限；
- 指向不存在任务的依赖；
- 自依赖或任意有向环。

`DagScheduler` 每轮只挑选所有父任务均成功的 ready 节点，通过 `asyncio` semaphore 有限并发。失败父节点的后代不会执行。单任务使用独立 timeout，只有 `RetryableTaskError` 和超时可在 `max_attempts` 内重试；取消令牌能中断正在等待的异步任务。

并发测试让两个根任务互相等待“双方都已启动”的事件，因此如果实现退化为串行，测试会直接超时；两个根任务结束后，依赖任务才进入执行。

## 7. C16：PostgreSQL Repository

提交信息：`feat(harness): persist runs tasks and events`

第一份 migration 创建：

- `runs`
- `tasks`
- `task_dependencies`
- `events`

表包含状态 Check Constraint、外键、幂等唯一键和租约候选索引。`PostgresHarnessRepository` 使用 SQLAlchemy async Core；Worker 领取任务时在一个事务内执行：

```sql
SELECT candidate ... FOR UPDATE SKIP LOCKED
UPDATE tasks SET state = 'leased', ...
RETURNING tasks.*
```

查询同时检查任务可用时间、deadline、租约、依赖状态和可选 run ID。`events` 通过 `(run_id, idempotency_key)` 唯一约束实现追加幂等。

`MemoryHarnessRepository` 实现相同协议，用锁模拟原子临界区，支持快速离线契约测试。它不是生产状态源。

Compose 新增一次性 `migrate` 服务：PostgreSQL 健康后运行 `alembic upgrade head`，成功后 API 才启动。也可以手动执行：

```powershell
pnpm db:sql
pnpm db:upgrade
```

## 8. C17：heartbeat、checkpoint、恢复与 Outbox

提交信息：`feat(harness): add checkpoints and recovery`

第二份 migration 创建 `checkpoints` 和 `outbox_events`。

- heartbeat 只允许租约所有者延长仍未过期的租约，防止旧 Worker 复活已转移任务。
- reaper 将过期 leased/running/waiting_tool/validating 任务转为 `waiting_retry`；尝试耗尽时转为 `failed`。
- checkpoint 以 `(task_id, step)` 唯一，重启后读取最大 step。
- `RecoveryCoordinator` 先释放过期租约，再由新 Worker 领取并读取最近检查点。
- 业务 Event 与 Outbox 行同事务写入；如果 Event 幂等键已存在，不创建第二条 Outbox。
- 多个 publisher 使用 `SKIP LOCKED` 风格的 Outbox 租约，发布成功后写入 `published_at`。

Outbox 是工程上标准的 at-least-once 语义：正常重启和并发 publisher 不会重复发送；若外部发送已经成功、进程却在本地标记前崩溃，仍可能重投。因此消费者必须用稳定 `event_id` 幂等处理，不能错误宣称跨系统 exactly-once。

检查点只保存恢复所需的结构化消息、游标和 Artifact 引用，不保存模型私有思维链或供应商不允许持久化的原始响应。
