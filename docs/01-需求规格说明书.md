# 基于多 Agent 的智能旅游攻略生成系统——需求规格说明书

> 文档版本：v0.1（调研基线）  
> 更新日期：2026-09-10  
> 项目状态：空仓库，尚未开始编码  
> 目标读者：产品设计、开发、测试、答辩/评审人员

## 1. 文档目的

本文档把用户提供的图片方案转换为一份可开发、可测试、可迭代的产品需求。图片仅作为早期设想，不作为已经实现的事实或不可修改的技术约束。

本项目要实现的不是“让几个大模型自由聊天”，而是一个由自建 Harness（运行时与编排器）管理、由多个职责明确的 Agent 协同、由确定性算法和可信数据工具兜底的旅行计划系统。

## 2. 背景判断与对原方案的修正

| 图片中的设想 | 问题 | 本方案修正 |
| --- | --- | --- |
| 数据采集器、数据处理器、方案生成器、方案评分器各算一个 Agent | 采集、清洗、金额计算、时间校验多为确定性工作，交给 LLM 会增加成本和幻觉 | 把采集/清洗/校验做成普通服务和工具；Agent 按业务判断能力划分 |
| 4 个 Agent 即完整架构 | 缺少任务分发、共享状态、冲突解决、终止条件和最终汇总者 | 增加 1 个 Coordinator（总控大脑）与自建 Harness；核心为 1+4，可按需扩展 |
| MCP 是所有外部数据的默认接入方式 | MCP 只是工具协议，不保证数据实时性、正确性、授权和稳定性 | 建立统一 Tool Adapter；生产链路优先官方 API/SDK，MCP 和 CLI 是可替换适配方式 |
| 高德、百度、Amadeus、小红书爬虫可直接组合 | 数据授权、接口存续、坐标系、缓存和爬虫合规均未处理；Amadeus Self-Service 已发生重大变化 | 国内地图以高德或百度二选一为主；航班/酒店做供应商适配与 Mock；不把小红书爬虫纳入 MVP |
| 直接使用 LangGraph + Celery + Redis | 对空仓库和毕业设计/MVP 过度工程化，也弱化“自建 Harness”的目标 | 首版使用自写状态机 + `asyncio` + PostgreSQL；达到横向扩展条件后再引入工作流/消息系统 |
| React + Leaflet 即可完成地图 | Leaflet 只是渲染库，底图、POI、路线、坐标系和许可仍需单独解决 | 国内 MVP 使用高德 JS API；全球版可切换 MapLibre GL JS + 合法瓦片供应商 |

## 3. 产品定位

### 3.1 一句话定义

用户输入目的地、日期、预算、成员和偏好后，系统通过多个自建 Agent 并行收集和分析信息，利用确定性约束优化生成 2～3 套可比较、可解释、可在地图上查看且带来源与更新时间的旅行攻略。

### 3.2 目标用户

- 需要快速规划 1～7 日城市旅行的中文用户。
- 希望在预算、节奏、交通时间、营业时间之间做权衡的自由行用户。
- 需要展示多 Agent 协作、工具接入和可解释规划能力的项目评审者。

### 3.3 MVP 假设

- 第一阶段服务中文用户，以中国大陆单城市、1～5 日行程为主。
- 系统提供规划与跳转，不自动购买机票、火车票、酒店或门票。
- 实时价格和余票只作为“查询时刻的参考”，必须展示来源和查询时间。
- 国内地图供应商首版只启用一家，避免 GCJ-02、BD-09、WGS84 混用。
- 大模型可以来自云端模型 API，也可以来自本地 Ollama/vLLM；无论哪种，Agent、协作协议、状态和工具执行均由本项目自己实现。

## 4. 产品目标与非目标

### 4.1 产品目标

1. 生成时间与空间上可执行的日程，而非只生成语言流畅的攻略文章。
2. 真实体现多 Agent 的任务分发、并行执行、结构化交付、审校和修复闭环。
3. 对关键事实保留来源、抓取时间、有效期和置信度。
4. 能对多套方案按预算、路程、偏好匹配和风险进行可解释对比。
5. 通过供应商无关的适配层降低对单一 API、MCP 或模型厂商的绑定。
6. 支持中断、恢复、超时、重试、成本限制和完整追踪。

### 4.2 非目标

- MVP 不代用户下单、支付、退改签或保存身份证件。
- MVP 不承诺价格、余票、营业时间在用户实际出发时仍然不变。
- 不使用未获授权的账号登录、验证码绕过或高频爬虫。
- 不把每个函数包装成 Agent；导出、坐标转换、缓存、排序和数值计算应是普通代码。
- 不追求一次覆盖全球所有交通和住宿供应商。

## 5. 核心用户旅程

### 5.1 创建旅行计划

1. 用户填写出发地、目的地、日期/天数、同行人、总预算、节奏、兴趣、必去/不去地点、饮食和无障碍要求。
2. Coordinator 解析需求，发现阻塞性缺失信息时只提出必要问题；非阻塞项采用明确默认值。
3. Harness 把任务并行分发给目的地情报 Agent 与交通住宿 Agent。
4. 候选数据经标准化、去重、来源标记和过期判断后写入本次运行的共享黑板。
5. 行程规划 Agent 读取结构化候选集，调用路线矩阵和约束优化器生成多套方案。
6. 审校 Agent 检查硬约束、证据、风险和说明质量；不合格项形成结构化修复请求。
7. Coordinator 最多执行两轮局部修复，随后汇总并输出结果。
8. 前端展示日程、地图、费用、方案对比、来源和 Agent 协作轨迹。

### 5.2 修改与重规划

用户可提出“第二天不要太早”“增加亲子景点”“预算降到 3000 元”等修改。系统应复用未过期数据和既有产物，只重跑受影响任务，不得默认从头执行全部 Agent。

### 5.3 降级体验

当实时接口不可用时，系统应明确显示：

- 哪个数据源失败、失败时间与影响范围。
- 使用了缓存、Mock、用户输入还是没有数据。
- 哪些结论仍可用，哪些需要用户在官方渠道复核。
- 不得用模型编造价格、余票、营业时间或路线时长填补空缺。

## 6. Agent 体系需求

### 6.1 总体形态：1 个总控 + 4 个核心 Agent

Coordinator 是“总控大脑”，负责拆解、分发、预算、状态推进、冲突处理和最终汇总。它由确定性状态机主导，只在需求理解、任务路由和最终表达等需要判断的节点调用模型。

| 角色 | 主要职责 | 允许使用的工具 | 必须产出 |
| --- | --- | --- | --- |
| Coordinator / Supervisor | 解析需求、创建 DAG、并发调度、合并产物、触发修复、终止运行 | Agent 调度、状态存储、模型网关；不直接绕过专家调用全部数据源 | `TripBrief`、`TaskGraph`、`FinalPlanBundle` |
| A1 目的地情报 Agent | 搜索并筛选景点、餐厅、街区、活动、开放时间、游玩时长、天气适配性 | POI、天气、受控网页检索、官方页面读取 | `DestinationResearchArtifact` |
| A2 交通与住宿 Agent | 城际交通候选、酒店候选、市内交通模式/换乘约束、入住约束、费用区间 | 地图枢纽信息、航班、酒店、许可的数据源 | `LogisticsArtifact` |
| A3 行程规划 Agent | 把候选信息转为 2～3 个日程草案；权衡兴趣、预算、时间窗和移动成本 | 由 Harness 在候选合并后生成的路线矩阵、约束优化器、预算计算器；原则上不直接访问互联网 | `PlanCandidatesArtifact`（内含多个 `ItineraryVersion`） |
| A4 审校与风险 Agent | 检查硬约束、证据、新鲜度、矛盾、过度安排、无障碍/天气风险并给出修复指令 | 规则校验器、证据读取；只读访问其他产物 | `CritiqueArtifact` |

### 6.2 可扩展 Agent

只有同时满足“有独立上下文或权限边界、需要判断、能并行或独立评测”时才新增 Agent。候选包括：

- 预算 Agent：复杂多币种、多人分摊和价格波动分析。
- 天气与安全风险 Agent：台风、高温、空气质量、户外替代方案。
- 个性化记忆 Agent：经用户明确授权后维护长期偏好。
- 国际旅行合规 Agent：签证、入境、保险和当地规则，仅引用权威来源。
- 内容策展 Agent：在有合法内容授权时提炼主题路线与文化背景。

不应独立成 Agent 的能力：JSON 清洗、坐标转换、数据库读写、金额相加、导出文件、API 重试、缓存和鉴权。

### 6.3 协作可见性

前端必须能展示一个简化的协作时间线：

- 当前阶段、每个 Agent 的状态和耗时。
- 任务依赖关系与并行分支。
- 每个 Agent 提交的结构化产物摘要。
- 审校发现的问题、修复对象和修复轮次。
- 工具调用只展示名称、状态、耗时和来源，不展示密钥、完整思维链或敏感原始数据。

## 7. 功能需求

### 7.1 需求输入

- **FR-001**：支持出发地、目的地、开始/结束日期或天数。
- **FR-002**：支持人数、成人/儿童/老人、行动不便等成员特征。
- **FR-003**：支持总预算或人均预算、币种、预算弹性。
- **FR-004**：支持兴趣标签、旅行节奏、早晚偏好、交通偏好、住宿偏好、饮食限制。
- **FR-005**：支持必去点、排除点、固定预约和固定时间窗。
- **FR-006**：输入必须经过结构化校验；日期冲突、预算为负、目的地缺失等不得进入规划阶段。
- **FR-007**：系统采用默认值时必须在最终方案中可见并允许用户修改。

### 7.2 数据获取与证据

- **FR-010**：所有供应商通过统一 Tool Adapter 接入，Agent 不依赖供应商私有响应格式。
- **FR-011**：POI 的供应商事实至少包含供应商 ID、名称、坐标、类别、地址、开放信息、价格信息和来源；未知价格必须显式标记为 `unknown`，不得猜测。游玩时长作为系统估计值单独存储，包含估计方法、范围和置信度，不得伪装成供应商事实。
- **FR-012**：路线至少包含模式、距离、预计时长、查询时间和供应商。
- **FR-013**：价格、营业时间、天气、余票等易变事实必须包含 `retrieved_at` 与有效期/新鲜度等级。
- **FR-014**：外部文字均视为不可信数据，不能覆盖系统指令、工具权限或任务目标。
- **FR-015**：同一实体跨来源时进行去重和冲突保留，不得静默选择看似更好的值。
- **FR-016**：供应商不可用时执行超时、有限重试、熔断和降级，不允许无限循环。

### 7.3 计划生成与优化

- **FR-020**：每个日程项必须包含开始/结束时间、地点、活动、预计费用、前往方式、移动时长和证据引用。
- **FR-021**：必须满足日期、固定预约、营业时间、每天起止时间和基本移动可达性等硬约束。
- **FR-022**：以偏好匹配、总路程、预算偏差、节奏、天气适配和多样性作为软约束进行评分。
- **FR-023**：默认生成“均衡、经济、轻松”三套方案；数据不足时允许只返回一套并说明原因。
- **FR-024**：预算计算由确定性代码完成，区分已知价格、估算区间和未计入费用。
- **FR-025**：规划失败时返回不可行原因和建议放宽的约束，不得输出表面完整但冲突的日程。

### 7.4 审校、比较与解释

- **FR-030**：审校器必须输出错误代码、严重级别、证据、受影响行程项和建议修复动作。
- **FR-031**：系统最多自动修复两轮；超过上限返回当前最佳结果与遗留问题。
- **FR-032**：方案比较至少包含总费用区间、景点数量、通勤时间、空闲时间、偏好覆盖、风险和证据覆盖率。
- **FR-033**：所有评分均显示维度分，不能只给出无法解释的总分。
- **FR-034**：最终文本不得引入结构化产物中不存在的新事实。

### 7.5 前端与输出

- **FR-040**：支持表单输入、自然语言补充和可视化标签编辑。
- **FR-041**：支持 Agent 执行进度流式更新和取消运行。
- **FR-042**：支持日历/时间轴与地图联动，点击日程项时定位对应地点与路线。
- **FR-043**：支持多方案并排对比和一键选定。
- **FR-044**：支持 Markdown、JSON、打印友好页面；ICS 与 PDF 作为增强功能。
- **FR-045**：地图或预订跳转必须打开官方/授权渠道，并提醒用户再次核实价格与可用性。
- **FR-046**：支持用户针对地点、某一天或整套方案反馈，反馈能触发局部重规划。

### 7.6 管理与评测

- **FR-050**：支持配置模型、Agent 最大步数、并发数、单次运行费用和时间预算。
- **FR-051**：支持启用/禁用供应商、健康检查、配额和失败率查看。
- **FR-052**：每次运行保留版本、事件、产物、模型/工具元数据和评测结果。
- **FR-053**：支持用固定数据快照重放运行，便于调试和答辩复现。
- **FR-054**：提供单 Agent 基线与多 Agent 方案的对照评测，证明拆分带来的价值。

## 8. 约束模型

### 8.1 硬约束

- 日期、时区和每天可活动时间。
- 固定预约/交通班次/入住退房窗口。
- POI 营业时间和必要预约限制。
- 相邻活动之间的路线时长与缓冲。
- 用户明确的排除项、无障碍和饮食禁忌。
- 预算硬上限（用户选择“不可超支”时）。
- 单日最大活动时长与最晚返回时间。

### 8.2 软约束

- 兴趣匹配、景点质量和主题一致性。
- 少走回头路、减少跨区移动。
- 用餐时间合理、每天保留休息和机动时间。
- 室内外活动与天气匹配。
- 热门与小众、文化与娱乐的多样性。
- 预算余量、价格稳定性和取消灵活性。

## 9. 输出数据要求

最终 `FinalPlanBundle` 至少包含：

```text
request_summary
assumptions[]
plans[]
  id / title / strategy
  days[]
    date / weather_summary / items[] / daily_budget / warnings[]
  total_budget_range
  score_breakdown
  unresolved_risks[]
comparison
evidence[]
collaboration_summary
generated_at / data_freshness
```

每条 `evidence` 至少包含 `source_name`、`source_url_or_provider_id`、`retrieved_at`、`field_paths`、`freshness` 和 `confidence`。对供应商条款不允许持久化的内容，仅在当前响应中展示。默认不落库原始供应商 payload；数据库只保存条款允许的 provider ID、请求元数据、脱敏参数哈希、来源引用和用户生成内容。若用户生成方案也包含受限制字段，则该方案只能临时展示或按获得的商业授权保存。测试 Fixture 必须是合成数据、自有数据或明确获准保存的数据，不能自动录制受限制的生产响应。

## 10. 非功能需求

### 10.1 正确性与质量

- **NFR-001**：Agent 输入输出必须通过版本化 JSON Schema/Pydantic 校验。
- **NFR-002**：硬约束校验通过率目标 100%；无法通过时不得标记为“可执行方案”。
- **NFR-003**：易变事实的来源和查询时间覆盖率不低于 95%。
- **NFR-004**：已知费用的程序化汇总误差为 0；估算必须以区间展示。
- **NFR-005**：硬约束相关事实必须区分 `verified`、`contradicted`、`unknown`。当用户声明为强制条件时，`unknown` 必须 fail-closed，要求人工确认或将方案标记为不可验证，不得标记为可执行。

### 10.2 性能与可靠性

- **NFR-010**：创建运行后 2 秒内返回运行 ID，并开始发送进度事件。
- **NFR-011**：在外部服务正常、3 天单城市请求下，MVP 完整生成 p95 不高于 90 秒。
- **NFR-012**：工具调用有独立超时；重试采用指数退避并设置总次数上限。
- **NFR-013**：服务重启后可从最近检查点继续，或明确终止并给出可重试状态。
- **NFR-014**：同一幂等键不得产生重复外部写操作或重复运行记录。

### 10.3 安全、隐私与合规

- **NFR-020**：服务端 Web Service/模型/商业数据 API 密钥只在服务端密钥存储或环境变量中出现，不进入提示词、前端、产物和日志。地图 JS API 必须使用独立的最小权限客户端 Key，并配置域名白名单和供应商要求的安全机制；客户端 Key 可见，不能被当作服务端秘密或复用服务端权限。
- **NFR-021**：工具按 Agent 白名单授权，默认只读；任何预订或写操作必须二次确认。
- **NFR-022**：对 URL 访问执行域名白名单、SSRF 防护、内容长度和 MIME 限制。
- **NFR-023**：只要启用持久化，用户就可删除自己的旅行记录；匿名 MVP 使用不可猜测的 run access token 鉴权，账号版使用 `user_id/tenant_id`。长期偏好仅在该功能启用并经显式授权时保存和删除。默认不保存身份证件、支付信息和精确常住地址。
- **NFR-024**：遵守地图、天气、酒店和内容供应商的展示、署名、缓存与再分发条款。

### 10.4 可维护性与可移植性

- **NFR-030**：更换模型或数据供应商不修改 Agent 核心业务代码。
- **NFR-031**：Harness 不依赖第三方 Agent 托管接口；核心状态机和消息协议归本项目所有。
- **NFR-032**：支持本地 Mock 模式，在没有任何外部密钥时完成端到端演示。
- **NFR-033**：所有公共模块具备类型检查、单元测试和结构化日志。

### 10.5 可观测性与成本

- **NFR-040**：记录 run、task、agent、model、tool 五级 trace，关联统一 `trace_id`。
- **NFR-041**：记录每次模型调用的模型名、延迟、token/估算成本和结束原因。
- **NFR-042**：记录每次工具调用的供应商、延迟、缓存命中、状态码和降级情况。
- **NFR-043**：达到步数、token、费用或墙钟时间预算时必须安全终止。

## 11. 验收标准

### 11.1 MVP 产品验收

1. 在无外部密钥的 Mock 模式下，输入“北京 3 天、2 人、预算 4000 元、历史与美食、节奏适中”，可生成至少两套完整方案。
2. 协作界面能看到 1 个 Coordinator 和 4 个核心 Agent 的任务状态、并行关系、产物与一次审校过程。
3. 任意相邻活动的移动时间都来自路线工具或明确标记的降级估算。
4. 注入一个“周一闭馆”冲突后，规则校验器能发现并触发局部修复。
5. 把预算降到不可行值时，系统返回不可行说明，而不是虚构低价。
6. 关闭天气接口时仍能生成方案，但所有天气相关结论被移除或标记缺失。
7. 重新提交相同幂等键不会创建第二份运行。
8. 最终 JSON 通过 schema 校验，Markdown 与页面内容来自同一份结构化对象。

### 11.2 多 Agent 有效性验收

- 建立至少 50 条固定测试请求，覆盖亲子、老人、无障碍、预算受限、雨天、跨区和固定预约。
- 比较单 Agent 基线与多 Agent 版本的硬约束错误率、证据覆盖率、平均路线时长、用户偏好覆盖和运行成本。
- 多 Agent 版本至少在硬约束错误率或证据覆盖率上有显著提升；若没有，应合并无价值的 Agent，而不是保留形式上的多 Agent。

## 12. 数据与业务边界

- 中国铁路 12306 官方渠道未提供本项目可依赖的公开开发者购票 API；MVP 不抓取、不代购，采用用户手工输入、授权商业供应商或官方跳转。
- 小红书公开开放能力主要面向电商与小程序，不等同于公开笔记搜索数据接口；MVP 不采集笔记和评论。
- 地图供应商常对缓存、展示和再分发有限制；上线前必须逐项完成许可检查。
- 航班和酒店报价会过期；展示时必须标记“查询时间”和“以供应商最终页面为准”。
- 签证、健康、安全等高风险信息只能来自政府、使领馆或其他权威来源，并显示更新时间。

## 14. 待用户确认的产品决策

以下决策不阻塞架构设计，但应在 P0 结束前确认：

1. 项目主要用于毕业设计/作品集，还是计划真实上线运营。
2. 首个演示城市和是否只覆盖中国大陆。
3. 可使用的云模型与预算，还是要求全本地模型。
4. 是否需要真实酒店/航班价格，或 Mock + 官方跳转即可。
5. 是否需要登录、长期偏好、分享链接和 PDF/ICS 导出。
